# คู่มือเล่นและนำเสนอ Sentinel SOC Learning Lab

ฉบับ 27 ต.ค. 2026 อ่านคู่กับ [ระบบปัจจุบัน](current-system.md) และ [สถานะส่งมอบ](presentation-readiness.md)
คู่มือนี้ไม่ใช่หลักฐานว่า deploy แล้ว หน้าจอ local อยู่ที่ `http://127.0.0.1:4175/learning`

## เริ่มเล่นอย่างไร

1. สมัคร/เข้าสู่ระบบด้วย email หรือ Google ผ่าน Supabase Auth หากบัญชีต้องยืนยัน email ให้ยืนยันก่อน บัญชีใหม่ได้ Analyst ไม่ใช่ Instructor
2. เปิด **เส้นทางเรียนรู้** `/learning` เริ่มระดับต้น อ่านบทเรียนทีละขั้น ทำตามคำอธิบาย request/response แล้วบันทึกความคืบหน้าให้ครบทุกบทของระดับ การอ่านจบยังไม่ใช่สอบผ่าน
3. เปิด `/practice` เลือกระดับ/หมวดและเคส อ่าน request, response และ log เลือกข้อสรุป ความรุนแรง หลักฐาน และเขียนเหตุผล บันทึกร่างได้ แล้วส่งคำตอบเพื่อดู feedback ตามกฎจาก server สีเขียว/แดงต้องอ่านคำอธิบายประกอบ ไม่ใช่ AI ตรวจแล้ว
4. เปิด `/knowledge-check` เพื่อตอบข้อเขียน 10 ข้อของระดับ ส่งครบทั้งชุดเพื่อเก็บประวัติบน DB ตอนนี้สถานะรอตรวจ ไม่สร้างคะแนนหรือใช้แทนการสอบผ่าน ข้อความที่ยังไม่ส่งยังไม่ได้บันทึกบน server
5. เปิด **สถานการณ์ฝึก** เลือก S02 แล้วเริ่ม training run ใน **รอบฝึกของฉัน** อ่าน event ที่ worker ปล่อยตามเวลา เลือก event เพื่ออ่าน request/response/log; pause/resume เพื่อควบคุมการปล่อยหลักฐาน ไม่ใช่หยุดด้วยการปิด browser
6. เปิด alert/ticket ตรวจเหตุผลและหลักฐาน เขียน assessment/note ลองแก้ไข ลบแบบ soft delete และ restore เพื่อดูประวัติ ก่อนกด finish เพราะรอบที่กำลังจบ/จบแล้วแก้คำตอบไม่ได้
7. กลับ `/learning` ดูส่วน **สอบภาคปฏิบัติและการเลื่อนระดับ** ทำบทเรียนให้ครบก่อนเริ่มสอบ ระหว่างสอบไม่มี Ask AI หรือเฉลย กด submit เพื่อ freeze คำตอบ
8. เมื่อ Instructor ที่ได้รับ assignment ตรวจแล้ว กด **ตรวจผลและสิทธิ์ล่าสุด** ถ้าผ่านเพียงหนึ่งเคสจะเห็น **เริ่มเคสสอบถัดไป** ต้องผ่านครบ 3 เคสของระดับจึงปลดล็อกระดับถัดไปตาม server ไม่ใช่ผ่านเคสแรกแล้วข้ามระดับ

บทบาทของแต่ละหน้า: บทเรียน = สอน, practice = ลองตอบพร้อม feedback, simulation = ฝึกทำงานกับเหตุการณ์ตามเวลาและ ticket, ข้อเขียน = เก็บคำตอบทบทวนรอตรวจ, practical exam = สอบแบบ blind เพื่อเลื่อนระดับ

## เตรียมก่อนถ่ายคลิป

- ใช้ URL ที่ deploy จริงสำหรับคลิปส่งงาน ไม่ใช้ local URL แล้วเรียกว่า deployed application
- เตรียมบัญชีผู้เรียนใหม่หนึ่งบัญชี บัญชีที่เรียนครบจริงหนึ่งบัญชี และ Instructor ที่มี assignment จริง ไม่แก้ DB เพื่อสร้างคะแนนผ่านสำหรับเดโม
- ทดสอบ API, worker, evaluator, session/Google callback และการบันทึกข้าม refresh บน environment ที่จะถ่ายจริง
- เตรียมเคส practice หนึ่งเคส, S02 หนึ่งรอบ และ ticket/note ที่ยังแก้ไขได้ ไม่เริ่มสอบค้างก่อนสาธิต training
- ถ้าจะสาธิต review ให้จัด assignment ผ่าน workflow/operator ที่รองรับก่อน ไม่ให้สิทธิ์ทุกบัญชีเพียงเพื่อถ่ายคลิป
- ซ่อน `.env`, รหัสผ่าน, connection string, token, cookies, Google OAuth secret และหน้าจอที่มีข้อมูลบัญชีอื่น
- ใช้ข้อมูล synthetic เท่านั้น ไม่เปิด URL หรือ execute payload ใน log

## สคริปต์ไม่เกิน 20 นาที

| เวลา | เนื้อหาและสิ่งที่เปิด | ประเด็นที่ควรพูด |
|---|---|---|
| 0–2 | ชื่อโครงงาน สมาชิกจริง และกลุ่มเป้าหมาย | “ผู้เริ่มต้นเห็น log แต่ไม่รู้จะดูตรงไหน เราจึงสอนอ่านหลักฐานก่อนฝึกวิเคราะห์และสอบเลื่อนระดับ” ไม่อ้างว่าแทน SOC production |
| 2–6 | Flow และ Architecture ใน current-system.md | แยกเรียน/ฝึก/สอบ, 3 ระดับ, เก็บ progress/คำตอบฝั่ง server, คนตรวจเป็นผู้ตัดสินในขั้นที่ยังรอตรวจ |
| 6–9 | แผนภาพ stack และ ER | Next.js App Router + React/TypeScript, FastAPI/Pydantic, SQLAlchemy async/asyncpg, Alembic, Supabase PostgreSQL/Auth, Python worker/evaluator แยกหน้าที่ Dify ยังไม่เชื่อมจริง |
| 9–10 | Login → บทเรียน | บันทึกขั้นเรียนแล้ว refresh ให้เห็นข้อมูลจาก server อธิบาย method/path/status และเหตุใด request เพียงรายการเดียวไม่ยืนยันผลโจมตี |
| 10–11 | Practice | ส่งข้อสรุปพร้อม evidence ดู feedback/เหตุผล และประวัติที่เก็บ DB ระบุชัดว่าใช้กฎ ไม่ใช่ผล Dify |
| 11–13 | S02 → event → ticket/note | pause/resume, อ่านหลักฐาน, create/update/delete/restore และ revision แสดง validation ด้วยข้อมูลไม่ครบโดยไม่โจมตีระบบจริง |
| 13–14 | ข้อเขียน + practical exam | ข้อเขียน 10 ข้อเก็บทั้งชุดรอตรวจ; practical exam submit แล้วแก้ไม่ได้ ไม่มี Ask AI ก่อนส่ง |
| 14–15 | ผลตรวจและ progression | Assigned Instructor review → ตรวจสิทธิ์ล่าสุด → ผ่าน X/3 → เริ่มเคสถัดไป/ปลดล็อกเมื่อครบ ไม่ต้องทำครบทุกข้อในคลิป |
| 15–17 | ความท้าทายและการแก้ | ตัวอย่างจริง: session มีแต่ยังเห็น login, error เริ่มรอบหาย, ผ่านเคสแรกแล้วปุ่มเคสถัดไปหาย, retry ข้อเขียนล้างคำตอบ อธิบาย regression tests และข้อจำกัด |
| 17–19 | สรุปและงานต่อ | สิ่งที่ทำได้จริง, งาน Dify/RAG และ public deployment acceptance ที่ยังค้าง ห้ามอ้าง mock เป็นผล AI จริง |
| 19–20 | Buffer/เครดิต | สมาชิก แหล่งอ้างอิง repository และ URL demo/เอกสาร |

## สไลด์ที่ควรเตรียม (9 หน้า)

1. ชื่อโครงงาน สมาชิก และปัญหาของผู้เรียนเริ่มต้น
2. กลุ่มเป้าหมายและขอบเขต: synthetic evidence ไม่โจมตีระบบจริง
3. User flow เรียน → ฝึก → สอบ → review → เลื่อนระดับ
4. หน้าที่ของแต่ละโมดูลและข้อแตกต่าง practice/simulation/exam
5. Architecture และเหตุผลเลือกเทคโนโลยี
6. ER/Database: user → progress/run → evidence → answers/revisions
7. Demo checklist และ CRUD/validation ที่จะเปิดจริง
8. ปัญหาที่แก้พร้อมหลักฐาน tests ไม่ใช้เพียงภาพหน้าจอ
9. ผลลัพธ์ ข้อจำกัด งานต่อ และลิงก์ส่งมอบ

ใช้แผนภาพใน current-system.md ได้โดยระบุว่าเป็น logical overview ส่วน schema/constraints จริงดู database.md และ migration graph ไม่จำเป็นต้องอ่านชื่อทุกตารางในคลิป

## ข้อความตอบอาจารย์ที่ควรแยกให้ชัด

- “ข้อมูลจำลอง” หมายถึงเหตุการณ์สังเคราะห์เพื่อความปลอดภัย ไม่ได้หมายความว่าคำตอบผู้เรียนเก็บใน browser ทั้งหมด
- “มีฐานข้อมูลแล้ว” ไม่ได้แปลว่า public web/API/worker/evaluator deploy ครบ
- “AI mock” เป็นตัวแทนทดสอบ ไม่ได้สร้าง log ด้วย AI และไม่ใช่คะแนน benchmark จริง
- RAG จะค้นคู่มือที่อนุมัติเพื่ออธิบายหลักการ แต่หลักฐานเหตุการณ์ต้องมาจาก request/response/log ของรอบนั้น
- ระบบปัจจุบันยังไม่มี Dify chatbot/ตรวจเหตุผลครบตามเป้าหมาย ข้อเขียนที่ส่งยังต้องรอระบบตรวจ ไม่ได้ auto-pass
- CRUD แสดงผ่าน ticket/note/draft ส่วน frozen submission และ audit ตั้งใจห้ามเขียนทับเพื่อรักษาประวัติ

## ส่งวิดีโอ

สำรองคลิป demo เผื่อเครือข่าย แต่ต้องบอกว่าเป็นคลิปสำรอง ไม่กล่าวว่าเป็น live deployment ที่กำลังทำงาน
